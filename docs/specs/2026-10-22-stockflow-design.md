# StockFlow：单仓库存与订单履约系统设计稿

日期：2026-10-22。状态：用户已授权在 D:\project 建立独立项目并实施。当前进入 P0，本文保留后续阶段的设计；实际完成范围见 ../progress.md。

## 1. 目标与项目组合

面向 Java 后端实习/校招，建立一个能独立解释、复现和验证核心设计的主打项目。课程里的中州养老后台承担常规业务开发与框架学习；本项目承担事务、并发正确性、幂等、状态变化、失败恢复及工程交付。

成功标准是：业务流程能运行，异常与并发场景有可重复测试，关键选择有理由，陌生环境能够按文档部署。性能与可靠性只报告实际测量和实验结果。

本次已确认的事实是用户选择库存与订单履约方向。单仓、自营、固定角色、模拟确认、命名 StockFlow 是本稿提出的范围，便于审阅后具体落实。

## 2. 方案比较与推荐

| 方案 | 收益 | 代价 | 决定 |
|---|---|---|---|
| 在 zzyl10 中加入订单库存 | 复用已有登录、权限和页面 | 混入养老课程业务，两个项目难以区分 | 不采用 |
| 独立的模块化单体 | 事务边界清楚，能独立开发与测试，部署成本低 | 需要自行组织业务与最小认证 | 推荐 |
| 订单、库存、用户分别做微服务 | 可以练习跨服务通信 | 过早引入分布式事务、服务发现与部署成本 | 当前不采用 |

采用一个后端进程、一个独立 MySQL schema 和一个前端。按业务包划分目录，不为每个实体建立独立 Maven 模块，不引入通用工作流引擎或自研 ORM。

## 3. 范围

- 一个仓库，按 SKU 管理实物商品；不处理多仓调拨。
- 商品状态、入库、库存查询、订单创建与查询、确认、取消、超时取消、发货和完成。
- 买家、仓管、管理员三类角色。买家只能访问自己的订单；仓管处理库存与发货；管理员负责基础设置。
- “确认订单”是演示业务命令，不代表接入支付，不处理退款、支付回调或真实结算。
- 订单最多包含 10 种不同 SKU，单 SKU 数量为 1–99；重复 SKU 在边界层合并并重新检查数量。
- 不做优惠券、推荐、全文检索、多租户、分库分表、复杂组织权限和真实物流接口。
- 前端仅提供演示核心流程需要的页面；不重做完整后台设计系统。

## 4. 技术与实现边界

- Java 17、Spring Boot、Spring Security、Bean Validation、MyBatis、MySQL/InnoDB。延续课程已有能力，避免为了区别而替换 ORM。
- 后端按 auth、catalog、inventory、order、fulfillment 包组织；Controller 校验请求，Service 明确事务，Mapper 显式表达条件更新。
- 第一阶段不依赖 Redis 或消息队列即可完成正确的订单库存流程。
- 后续阶段加入 Redis 商品摘要缓存与 RabbitMQ 事件通知，分别形成可验证的学习增量。
- 使用 Spring 的测试支持进行单元与集成测试，数据库正确性测试使用独立 MySQL 环境。
- 以 Docker Compose 和 GitHub Actions 完成可复现环境和自动构建测试。引入这些配置时使用稳定版本并固定依赖。
- 不改课程的 Spring Boot 版本，不复用 zzyl10 数据库或它的配置口令。新项目具体依赖版本在实施计划中锁定，并验证 Java 17、MyBatis 与数据库组合。
- 标识使用数据库自增 ID；当前无需分布式 ID。商品金额使用 BigDecimal 与 DECIMAL，客户端只提交 SKU 和数量，价格由后端读取并快照。
- 最小认证只实现必要登录与角色/资源授权。借用课程或上游代码时保留许可证及来源，业务核心独立实现，不整体复制课程项目再换名。

## 5. 核心模型

业务最小模型：

| 表 | 关键字段与约束 | 职责 |
|---|---|---|
| sku | id、唯一编码、名称、价格、状态 | 商品定义 |
| inventory | sku_id 唯一、on_hand、reserved | 实存量与已预留量；可用量计算为 on_hand - reserved |
| customer_order | id、buyer_id、request_key、payload_hash、status、expires_at、总额、时间 | 订单与创建请求幂等；唯一键 buyer_id + request_key |
| order_item | order_id、sku_id、数量、单价快照；order_id + sku_id 唯一 | 不可在下单后随意修改的订单明细 |
| inventory_ledger | sku_id、order_id/业务操作键、类型、数量与时间；操作类型 + 操作键 + sku_id 唯一 | 对预留、释放、出库和入库进行可核对记录 |

库存始终满足 on_hand >= reserved >= 0。第一版不增加独立 available 字段，也不增加与订单明细重复的预留表。

后续异步阶段增加 outbox_event 和 notification_record：前者记录待投递事件；后者使用唯一 event_id 记录模拟通知结果，支持幂等消费。这里只展示站内通知结果，不发送外部短信、邮件或第三方消息。

所有业务数据使用独立开发和测试 schema，例如 stockflow_dev 和 stockflow_test。课程库 zzyl10 不是迁移目标。

## 6. 订单状态与库存变化

| 命令 | 允许状态 | 结果状态 | 库存变化 |
|---|---|---|---|
| 创建 | 无订单 | PENDING_CONFIRM | reserved 增加，on_hand 不变 |
| 确认 | PENDING_CONFIRM 且未到期 | CONFIRMED | 无 |
| 买家取消 | PENDING_CONFIRM | CANCELLED | reserved 减少，on_hand 不变 |
| 超时取消 | PENDING_CONFIRM 且已到期 | CANCELLED，原因为 EXPIRED | 同上 |
| 发货 | CONFIRMED | SHIPPED | reserved 和 on_hand 同时减少 |
| 完成 | SHIPPED | COMPLETED | 无 |

CONFIRMED 不允许买家取消；售后和退款不属于本范围。已发货不能再次发货。终态不会回到待确认。

同一命令的重试若目标状态已达到，返回现有结果且不重复改变库存；其他非法状态返回业务冲突。取消原因作为字段保存，不再增加一套含义重复的状态。

## 7. 事务、并发与幂等

### 创建订单

一次数据库事务完成：校验 SKU 与服务端价格、建立订单和明细、按 SKU ID 升序预留库存、写库存流水。预留采用带库存条件的数据库原子更新，受影响行数不足就整体回滚。

先插入受唯一键保护的 buyer_id + request_key，避免同一成功请求重复占库存。payload_hash 对规范化的 SKU 和数量计算；相同键、相同内容返回原订单，相同键、不同内容返回冲突。

唯一键冲突后的原订单查询在失败事务结束后进行，不能继续使用已标记回滚的事务。库存不足等失败请求不承诺保存创建结果，重试时重新校验库存。

所有多 SKU 操作使用相同的库存行访问顺序，降低死锁概率；对数据库死锁回滚可做少量、有限的整笔事务重试，不能只重试最后一条 SQL。

### 确认、取消和发货

先在事务中锁定目标订单行，再验证所有者、状态和时限，随后更新订单及必要的库存和流水。并发确认与取消只能有一个合法结果。

确认已到期订单返回冲突，不确认订单；超时任务负责释放库存。数据库时间作为超时判断依据，测试通过可控时钟/到期数据构造验证。

发货事务只接受 CONFIRMED，检查库存预留与实存，完成扣减和状态改变。任何一项失败整体回滚，禁止“订单发货成功但库存未扣减”。

数据库与事务是库存正确性的边界；Redis 分布式锁不作为初版前提。

### 超时回收

通过数据库索引扫描 status = PENDING_CONFIRM 且 expires_at 已过期的订单 ID，分批调用事务性取消流程，并在事务中再次检查条件。任务重复执行或服务重启不会重复释放库存。

## 8. 缓存和异步事件的后续增量

### Redis

只缓存商品展示摘要，采用短 TTL 与提交后删除缓存。允许商品展示的短暂最终一致性；下单时重新从数据库校验价格和状态。缓存不可用时回退数据库，不允许缓存数据决定可售库存。

测试覆盖缓存命中、修改后失效、过期及 Redis 不可用；不把引入 Redis 本身写成性能优化成果。

### RabbitMQ 与 outbox

发货等事务在同一个 MySQL 事务内写入 outbox 事件。独立轮询任务通过数据库条件领取事件并设置可过期的租约，在事务外投递消息，收到 broker 确认后记录投递结果。

使用持久化交换机和队列、持久化消息及发布确认；同时检查不可路由消息的退回，不能把发布确认误当成消息已经进入正确队列或已被消费。不可路由、否定确认和连接中断均进入失败恢复流程。

崩溃可能发生在消息已被接收、投递标记尚未写回之间，因此明确采用至少一次投递，而不声称恰好一次。通知消费者在本地事务内根据唯一 event_id 写通知记录；成功提交后确认消费，重复消息不会产生第二条通知记录。

失败采用有限次数退避重试，超限事件标记为 FAILED 并允许管理员显式重试；重试保留原 event_id。租约过期可重新领取，避免事件永久停留在处理中。

通知消费失败使用有次数限制的退避重试，超过 5 次转入持久化死信队列并记录待处理信息；管理员可以重放同一 event_id。禁止通过无限立即重新入队掩盖持续失败。

消息只用于模拟通知，不在消费者中再次改变订单和库存，因此消息重复或乱序不应破坏核心交易。暂不设计通用消息平台。

## 9. API 与错误处理

演示 API 按商品、库存、我的订单、仓管履约和管理员重试划分：

- 商品查询和管理、入库与库存查询。
- 创建订单、我的订单列表和详情、确认与取消。
- 仓管待发货查询、发货、完成记录。
- 异步阶段的通知结果、失败事件查询与管理员重试。

HTTP 语义统一：401 未登录、403 无角色权限、404 不存在或对买家不可见的资源、409 库存/状态/幂等内容冲突、400 请求字段非法。错误响应包含稳定业务码和 requestId，不返回堆栈、数据库口令或内部 SQL。

请求 DTO 不接受用户提交审计人、订单状态、订单总额或库存余额。操作人来自认证上下文。演示数据使用合成数据。

## 10. 验证与验收

| 场景 | 预期 |
|---|---|
| 初始库存 10，100 个不同请求并发下单，各买 1 件 | 请求全部结束且无技术错误时恰好 10 个成功、90 个库存不足；无取消前 reserved 为 10，库存不为负 |
| 同一买家同一创建键并发重试 50 次 | 最终成功响应指向同一订单，库存只预留一次 |
| 同一创建键换一个数量 | 返回冲突，不生成第二笔订单或改变原明细 |
| 多 SKU 中某项不足 | 整笔回滚，无残留订单、明细、预留或库存流水 |
| 确认与取消并发 | 最多一个状态变化生效，库存满足最终状态 |
| 确认与超时取消并发 | 到期条件与状态在同一事务内判定，不出现确认成功后仍释放库存 |
| 同一订单重复发货 | on_hand 和 reserved 只扣一次 |
| 买家访问别人的订单 | 不返回他人订单内容，且无法确认或取消 |
| 数量非法、负价客户端伪造金额、非法状态字段 | 拒绝非法数量，不信任客户端金额或状态 |
| 发货过程中制造数据库异常 | 订单、库存和流水一致回滚 |
| 超时任务重复扫描或重启 | 已取消的订单不再次释放库存 |
| Redis 关闭或失效竞争 | 展示可能降级，库存和下单价格仍由 MySQL 保证 |
| broker 停机、发布后崩溃、消费者重复接收 | 事件最终可恢复，模拟通知结果不重复 |
| 查询压力测试 | 保存环境、数据量、并发、持续时间、错误率和延迟分布，并核对正确性 |

数据库并发与事务测试运行在独立 MySQL 实例/schema，不能以 H2 或 mock 代替实际锁与事务语义。测量前后使用同一负载条件，不预设和编造吞吐数字。

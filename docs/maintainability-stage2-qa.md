# StockFlow 第二阶段：单据列表查询与后端可读性

日期：2026-10-29。改动基准：`255ed05b4804740fb55f28746a6f29bcabeb2cf2`。发布提交及云端状态见现有 PR 的最新提交和检查。

## 问题与改动

`GET /api/receipts` 和 `GET /api/returns` 原先查询总数与当前页，再为每张单据单独读取明细，即非空页执行 `2 + N` 次单据查询。

本阶段保留完整列表响应：先取得已筛选、已授权的当前页单据，再用这一页的 ID 一次读取明细，在内存按父单据归组，沿用原响应模型。详情与写入操作继续使用单据级查询。空页直接返回，避免生成空的 `IN` 条件。

两个批量查询使用参数绑定，不拼接用户输入；每次至多绑定当前页的100个单据ID。沿用明细表既有的“父单据ID、SKU”联合唯一索引，没有增加索引或迁移。明细按父单据、SKU排序，因此每张单据内仍按SKU排列。总数、分页和明细仍处于原有只读可重复读事务，避免混用多个数据快照。

`DocumentService` 同时展开原先多条语句挤在一行的写法，显式列出导入。创建、确认、取消、幂等键、库存锁、流水和审计的规则及事务边界保持原样。两个内部明细行模型仅携带归组用的父ID，不增加接口字段。不引入通用分页框架、缓存、XML映射层或新的运行依赖。

## 实际查询次数

测试通过真实HTTP请求进入控制器，并使用仅在测试中注册的MyBatis拦截器，在JDBC语句prepare时计数。统计范围只包含receipt_document、receipt_item、customer_return、return_item四张表的SELECT；不将认证、事务控制或测试夹具SQL计入。

| 场景 | 修改前实测 | 修改后实测 |
|---|---:|---:|
| 100条入库单，包含各单明细 | 102 | 3 |
| 100条退货单，包含各单明细 | 102 | 3 |
| 1条、8条入库单或退货单 | 未另作修改前测量 | 均为3 |
| 空的入库单或退货列表 | 未另作修改前测量 | 均为2 |

这是SQL往返次数的对比，不代表响应时间快了34倍，也不是生产吞吐量测试。关键字包含匹配、COUNT、深页OFFSET及潜在filesort仍沿用原实现，需要出现具体瓶颈后再优化。

## 验证结果

- 优化前，同一回归的两种100条列表均实际捕获102条SELECT，按预期失败；优化后全部通过。
- 新增5项真实MySQL集成测试，覆盖1／8／100条页面、超过最大页码时回落末页、空页、字面量`%_!`筛选、状态筛选、不同买家隔离、仓管与管理员访问、未登录及无权限、页码与页大小参数边界。
- 各单据的明细归属、数量、SKU顺序、名称／编码／单价快照、历史NULL名称保持正确；列表单据与对应详情响应一致；父ID内部字段不进入响应。
- 既有9项入库退货业务回归通过，包含并发确认、幂等、库存上限、流水冲突、晚行失败整体回滚等场景。
- 本地全量后端：101项通过、0失败、0错误、1跳过。跳过项为未开启的10000订单数据量测试，云端工作流另行执行。
- 前端89项通过、0失败、0跳过。Maven verify和运行包生成成功。

## 重现方式

配置独立的`stockflow_test`测试库、测试凭据与演示账号环境变量后，可执行：

```text
mvn -B -Dtest=DocumentQueryIntegrationTest,DocumentIntegrationTest test
```

新回归文件为`src/test/java/io/github/stockflow/DocumentQueryIntegrationTest.java`。测试清理夹具前强制核对数据库名为stockflow_test；不要将测试连接指向开发或业务库。数据库与口令保留在忽略目录／环境变量中。
